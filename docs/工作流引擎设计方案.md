# 工作流引擎设计方案

> 目标：把「流程」从代码里搬出来，变成项目经理能自己搭的配置。
> 本文所有表名/字段名都对齐现网库 `data/motor_pm_v2.db` 与 `backend_v2/models/`。
>
> **落地前提（贯穿全文）：只新增，不改不删已有表和已有数据。** 现有 85 个流程节点、
> 10 个阶段、17 个在跑的项目全部原样保留，新引擎通过"导入"而不是"替换"接入。

---

## 0. 先说清楚：新引擎和现有东西的接缝

现在平台上的"工作流"其实是**代码常量** `backend_v2/routes/training_process.py::PHASE_NODES`：
85 个节点，分 10 个阶段（硬件 `P0/PP1-PP5`、软件 `S0-S3`），每个节点长这样：

```python
{"seq": 1, "name": "需求调研与澄清", "venue": "线下",
 "roles": ["项目经理", "商务经理"],           # ← 现成的节点级权限雏形
 "actions": "...", "output": "需求调研报告",
 "handoff": "交项目组", "module": "阶段交付物矩阵 → 需求调研报告",
 "deadline": "G-S0 前(可选)", "tip": "..."}
```

步骤状态是**推导**出来的，不落库：交付物标准（`gate_deliverable_standard`）+ 人工确认
（`project_workflow_step_confirm`）+ 门禁签核（`gate_signoff_record`）三者拼出"这一步做没做完"。

这跟需求里的"状态节点"**不是一回事**，必须先把这层说破，否则设计会拧：

| | 现有 `PHASE_NODES` | 本次要做的引擎 |
|---|---|---|
| 粒度 | **项目级宏观流程**（从合同到售后，85 步） | **工作项级状态机**（每个需求/任务/缺陷/风险各自流转） |
| 一个项目同时处于几个状态 | 1 个（`Project.current_phase_id`） | N 个（每个工作项各1个，互不相干） |
| 定义位置 | Python 常量 | 数据库表 + 模板版本 |
| 谁能改 | 改代码发版 | 项目经理在项目内改 |

**两者不是替代关系，是分层**：宏观 85 步管"项目走到哪了"，新引擎管"这一条需求/缺陷现在什么状态、谁能动它"。
接缝只有一个字段：`wf_state_def.phase_code`——状态节点可选地挂到一个阶段码上（`P0`/`S0`…），
这样工作项状态能自动汇总回现有的阶段视图和跨项目统计，**不用改现有任何一张表**。

现有 85 节点不会丢：它会作为模板 A/B 的 **v1 只读基线**导入（`wf_template_version.baseline_source = 'PHASE_NODES'`），
项目经理可以"从基线复制一份到自己项目再随便改"。这样既满足"自由搭建"，又保证 17 个在跑的项目行为不变。

## 1. 平台底层：四类原子能力的数据结构

### 1.1 工作项元模型（定义身份，不定义流程）

三层拆开：**身份**（`work_item`）/ **类型**（`work_item_type`）/ **属性**（`work_item_attr_def` + `value`）。
流程相关的字段一个字都不放这里。

```
work_item_type                 工作项类型定义（需求/任务/缺陷/风险，可扩展）
  id                INTEGER PK
  project_type      VARCHAR(16)   归属项目类型；NULL = 全类型通用
  code              VARCHAR(32)   requirement / task / defect / risk / ...
  name              VARCHAR(64)   显示名
  icon              VARCHAR(32)
  allow_hierarchy   BOOLEAN       是否允许父子（需求=是，缺陷=否）
  allow_dependency  BOOLEAN       是否允许依赖
  allow_relation    BOOLEAN       是否允许具名关联
  default_state_code VARCHAR(32)  新建时落哪个语义状态（如 not_started）
  is_active         BOOLEAN
  UNIQUE(project_type, code)


work_item                      工作项实例（统一身份层，全平台唯一 ID）
  id                INTEGER PK
  project_id        INTEGER FK project.id      NOT NULL
  item_type         VARCHAR(32) FK work_item_type.code
  key               VARCHAR(32)   人可读编号，项目内唯一：REQ-012 / BUG-007
  title             VARCHAR(256)  NOT NULL
  description       TEXT
  state_id          INTEGER FK project_wf_state.id     ← 当前状态，指向项目自己的状态定义
  state_entered_at  DATETIME      进入当前状态的时间（用于"停留超时"类自动化）
  is_blocked        BOOLEAN       由依赖关系自动维护，见 §7
  owner_user_id     INTEGER FK user_auth.id    当前负责人（**按人，不是角色**）
  priority          VARCHAR(8)
  source_kind       VARCHAR(16)   manual / import / ai / automation
  ext               TEXT          JSON：类型特有但不必建索引的杂项
  created_by        VARCHAR(64)   账号名，风格同 audit_log.username
  created_at / updated_at / closed_at
  UNIQUE(project_id, key)
  INDEX(project_id, item_type, state_id)
  INDEX(owner_user_id)


work_item_attr_def             属性模型（每个类型有哪些字段，可配）
  id                INTEGER PK
  item_type         VARCHAR(32) FK work_item_type.code
  code              VARCHAR(32)   字段码，如 severity / due_date / spec_value
  name              VARCHAR(64)   显示名
  field_type        VARCHAR(16)   text/number/date/select/multiselect/user/bool/file
  options           TEXT          JSON，select 类用
  required          BOOLEAN
  default_value     TEXT
  editable_in_states TEXT         JSON 状态码数组；空=所有状态可编辑
  visible_in_states  TEXT         JSON
  is_indexed        BOOLEAN       常用作筛选条件的置 true
  sort_order        INTEGER
  UNIQUE(item_type, code)


work_item_attr_value           属性值（EAV，只为扩展属性服务）
  id                INTEGER PK
  work_item_id      INTEGER FK work_item.id
  attr_def_id       INTEGER FK work_item_attr_def.id
  value_text        TEXT
  value_num         REAL
  value_date        DATE
  value_ref_user    INTEGER FK user_auth.id
  value_json        TEXT
  UNIQUE(work_item_id, attr_def_id)
```

**与现有表的桥接**：现有 `requirement` / `task` / `risk_issue` / `test_issue` 四张表
**一行都不动、不加列**。新增一张映射表把老记录挂到新身份上：

```
work_item_source_map
  work_item_id      INTEGER FK work_item.id
  source_table      VARCHAR(32)   'requirement' / 'task' / 'risk_issue' / 'test_issue'
  source_id         INTEGER
  UNIQUE(source_table, source_id)
  INDEX(work_item_id)
```

老记录第一次被新引擎碰到时补一条映射，之后两套并存、双向可见。**不迁移、不删除**，
老页面照旧读写老表，新引擎读写 `work_item`，映射层保证是同一件事。

### 1.2 关系模型（三种关系原子）

一张表 + 一张类型字典。三种关系都需要**环检测**，在服务层用递归 CTE 做，不靠数据库约束。

```
wf_relation_kind               关系类型字典（三种原子 + 具名子类）
  id                INTEGER PK
  kind              VARCHAR(16)   hierarchy / dependency / link     ← 三种原子
  code              VARCHAR(32)   子类码
  name              VARCHAR(64)
  #  hierarchy:  parent_child(父子) / epic_story(史诗-故事)
  #  dependency: blocks(阻塞) / depends_on(前置) / relates_to(相关)
  #  link:        verifies(验证) / introduces(引入) / duplicates(重复) / causes(导致)
  parent_kind       VARCHAR(16)   具名关系归属哪个原子
  is_symmetric      BOOLEAN       对称关系（重复/相关）存一条即可
  inverse_code      VARCHAR(32)   反向码，用于渲染"被谁阻塞"
  allow_cross_project BOOLEAN
  UNIQUE(kind, code)


work_item_relation             关系实例
  id                INTEGER PK
  project_id        INTEGER FK project.id         冗余，便于按项目查
  kind              VARCHAR(16)   hierarchy / dependency / link
  code              VARCHAR(32)   具名子类，见上
  from_item_id      INTEGER FK work_item.id       NOT NULL
  to_item_id        INTEGER FK work_item.id       NOT NULL
  # dependency 专用
  dep_type          VARCHAR(8)    FS / SS / FF / SF   默认 FS(前置完成后继才可开始)
  lag_days          INTEGER       默认 0，可为负（提前量）
  # 元数据
  created_by        VARCHAR(64)
  created_at        DATETIME
  note              VARCHAR(256)
  CHECK(from_item_id <> to_item_id)
  INDEX(project_id, kind, from_item_id)
  INDEX(to_item_id, kind)

  -- 层级：一个工作项只能有一个父
  UNIQUE INDEX uq_hier_parent ON work_item_relation(from_item_id)
    WHERE kind = 'hierarchy'
  -- 对称关系去重：存的时候统一 (小id → 大id)
  UNIQUE INDEX uq_sym_link ON work_item_relation(from_item_id, to_item_id, code)
    WHERE kind = 'link' AND code IN ('duplicates','relates_to')
```

**三种关系各自的硬规则**（服务层强制，不是建议）：

| 关系 | 硬规则 |
|---|---|
| 层级 | 单父；禁止成环；父删除时子项**上提**到祖父，不级联删 |
| 依赖 | 禁止成环（`A→B→A`）；`FS` 且在途时把后继置 `is_blocked=1`；`FF/SS/SF` 只做展示提示不自动阻塞 |
| 具名关联 | 对称关系存一条并规范化端点顺序；`verifies` 允许 `缺陷→需求`/`测试→需求` 两种方向 |

### 1.3 权限原子（四个动作，绑到人）

与现有的**模块级**权限（`user_auth.permissions` 的 16模块×5动作）是**两根正交的轴**：

- 模块权限回答："你能不能进「项目台账」这个功能"（现有，管菜单和路由）
- 状态权限回答："进去之后，你能不能把**这一条**工作项**从这个状态**推到**那个状态**"（本文新增）

**两者是 AND：两道都过才能操作。** 判定在服务端，不在前端。

```
wf_node_acl                    状态节点权限（模板级默认）
  id                INTEGER PK
  owner_kind        VARCHAR(16)   'template_version' / 'project'
  owner_id          INTEGER       对应的 template_version.id 或 project_id
  state_id          INTEGER       模板级指向 wf_state_def.id，项目级指向 project_wf_state.id
  subject_type      VARCHAR(16)   user / project_role / department / permission_role / wf_group
  subject_id        INTEGER       对应表的 id；subject_type='pm' 时忽略此项
  can_enter         BOOLEAN       能进入本状态（承接流转）
  can_exit          BOOLEAN       能发起离开本状态
  can_edit_fields   TEXT          JSON 字段码数组；["*"] = 全部
  can_force_drag    BOOLEAN       强制拖拽（**不继承，必须显式授予**）
  can_assign        BOOLEAN       能改 owner
  INDEX(owner_kind, owner_id, state_id)
  UNIQUE(owner_kind, owner_id, state_id, subject_type, subject_id)
```

**主体现有表全都在，直接用，不新造**：

| subject_type | 指向 | 语义 | 例子 |
|---|---|---|---|
| `user` | `user_auth.id` | 具体某个人 | 张翔 |
| `pm` | — (按 `ProjectMember.role.name='项目经理'` 实时算) | 本项目 PM | 自动，不用配 |
| `project_role` | `role.id` × 本项目 | 本项目内的某角色组 | 本项目的测试工程师 |
| `department` | `department.id` | 部门 | 研发部全员 |
| `permission_role` | `permission_role.id` | 系统权限角色组 | 内置"查看者" |
| `wf_group` | `wf_group.id` | 临时组 | "PP3 评审组" |

```
wf_group                       临时用户组（现有的部门/角色覆盖不到时才用）
  id / project_id / name / desc / created_by / created_at
wf_group_member
  id / group_id / user_id / UNIQUE(group_id, user_id)
```

**解析优先级（后端实现，前端只展示结果）**：

```
1. user 显式授予      —— 命中即终局（允许或显式拒绝，都不再往下看）
2. wf_group
3. project_role
4. department
5. permission_role
6. 模板级 wf_node_acl 同名规则
7. 兜底：node.roles（从 PHASE_NODES 导入的默认）
```

冲突规则：**`can_enter`/`can_exit`/`can_edit_fields` 取并集（allow wins）**；
**`can_force_drag` 取交集（deny wins），且永不从上层继承**——强制拖拽是危险动作，
必须是有人明确点过头的。

### 1.4 自动化引擎（四原子：触发 / 动作 / 失败回退 / 审计）

```
wf_automation_rule             自动化规则
  id                INTEGER PK
  owner_kind        VARCHAR(16)   'template_version' / 'project'
  owner_id          INTEGER
  name              VARCHAR(128)
  phase             VARCHAR(16)   pre_transition ← 流转**前**，可阻断
                                  post_transition ← 流转**后**，不可阻断，只补偿
                                  standalone     ← 独立触发（定时/事件），不挂流转
  priority          INTEGER       数字小的先跑
  stop_on_match     BOOLEAN       本规则命中后不再跑后续规则
  trigger_json      TEXT          {"event":"state.entered","state_codes":["pending_review"]}
  condition_json    TEXT          见下 §6.2 条件表达式
  action_json       TEXT          [{"type":"assign_user","target":"...","params":{...}}]
  on_failure        VARCHAR(16)   retry / skip / compensate / block_transition
  retry_max         INTEGER       默认 3
  retry_backoff     VARCHAR(16)   none / linear / exp
  is_active         BOOLEAN
  created_by / created_at / updated_at


wf_automation_run              一次规则执行（幂等与重试的载体）
  id                INTEGER PK
  rule_id           INTEGER FK wf_automation_rule.id
  project_id        INTEGER
  work_item_id      INTEGER
  trigger_event     VARCHAR(64)
  idempotency_key   VARCHAR(128) UNIQUE   ← 见下
  status            VARCHAR(16)   pending / running / succeeded / failed / compensated / blocked
  attempt           INTEGER       默认 1
  input_snapshot    TEXT          JSON：触发时的上下文（不依赖当时的库状态）
  error             TEXT
  started_at / finished_at
  INDEX(project_id, work_item_id)
  INDEX(status, started_at)


wf_automation_action_log       单个动作的执行与补偿
  id                INTEGER PK
  run_id            INTEGER FK wf_automation_run.id
  seq               INTEGER       规则内顺序
  action_type       VARCHAR(32)
  params_json       TEXT
  status            VARCHAR(16)   pending / succeeded / failed / skipped / compensated
  result_json       TEXT
  error             TEXT
  compensable       BOOLEAN       是否可补偿（由动作类型决定，见 §6.3）
  compensated_at    DATETIME
  compensation_json TEXT          补偿实际做了什么
```

**幂等键**：`idempotency_key = "{rule_id}:{work_item_id}:{trigger_event}:{state_id}:{attempt_bucket}"`。
重试不会重复发通知/重复建任务——这是重试机制能用的前提。

**审计**：不建新表，全部落现有 `audit_log`：
`action='wf_auto'`、`entity_type='work_item'`、`entity_id=work_item.id`、
`details` 存 `{rule_id, run_id, trigger, actions:[...], result}`。这样现有的审计查询页面直接能用。

## 2. 模板层数据结构

```
wf_template                    模板（四类，平台维护）
  id                INTEGER PK
  code              VARCHAR(8)    A / B / C / D
  name              VARCHAR(128)  「合同交付类·电机电控系统集成开发」
  category          VARCHAR(16)   contract(合同交付类) / internal(内部研发类)
  project_type      VARCHAR(16)   映射到现有 project.project_type，见 §8
  desc              TEXT
  current_version_id INTEGER      当前生效版本
  is_active         BOOLEAN
  UNIQUE(code)


wf_template_version            模板版本（各自独立版本线）
  id                INTEGER PK
  template_id       INTEGER FK wf_template.id
  version_no        INTEGER       1,2,3… 每个模板各自递增
  status            VARCHAR(16)   draft / published / deprecated
  baseline_source   VARCHAR(32)   NULL / 'PHASE_NODES'（从现有85节点导入）
  change_note       TEXT
  published_by      VARCHAR(64)
  published_at      DATETIME
  created_at
  UNIQUE(template_id, version_no)


wf_state_def                   状态定义（模板级）
  id                INTEGER PK
  version_id        INTEGER FK wf_template_version.id
  code              VARCHAR(32)   版本内唯一，如 pending_review
  name              VARCHAR(64)   **显示别名**，PM 想叫什么叫什么
  semantic_state    VARCHAR(16)   **标准语义，不可改**，见下
  phase_code        VARCHAR(16)   可选，挂到现有阶段码（P0/PP1…/S0/S3）用于汇总
  sort_order        INTEGER       画布顺序，也是"跳过"判定的依据
  lane              VARCHAR(32)   泳道（通常是阶段码或部门），跨泳道不算"跳过"
  is_initial        BOOLEAN       每个版本有且仅有一个入口
  is_terminal       BOOLEAN
  is_verification   BOOLEAN       **验证节点**：被跨过时要填原因并补验证
  wip_limit         INTEGER       可选，看板列在制品上限
  color             VARCHAR(16)
  UNIQUE(version_id, code)

  -- 标准状态语义枚举（跨项目统计一致性的唯一保证）
  -- not_started(未开始) / in_progress(进行中) / pending_review(待评审)
  -- pending_verification(待验证) / done(已完成) / blocked(已阻塞) / cancelled(已取消)


wf_transition_def              流转规则（模板级）
  id                INTEGER PK
  version_id        INTEGER FK wf_template_version.id
  from_state_id     INTEGER FK wf_state_def.id      NULL = 任意状态（万能入口）
  to_state_id       INTEGER FK wf_state_def.id
  name              VARCHAR(64)   "提交评审"
  guard_json        TEXT          **进入/退出条件**，见 §6.2
  must_pass_states  TEXT          JSON 状态ID数组：本流转**必须**经过这些状态，顺序不满足即拒绝
  require_signoff   BOOLEAN       是否需要签核（复用 gate_signoff_record 的两级模型）
  allow_force       BOOLEAN       是否允许 PM 强制拖拽（默认 true，个别流转可禁）
  sort_order        INTEGER
  INDEX(version_id, from_state_id)


wf_node_acl_def                默认节点权限（模板级）—— 结构同 §1.3 的 wf_node_acl
wf_task_template               默认任务分解方式（模板级）
  id / version_id / item_type / name
  mode              VARCHAR(16)   none / checklist / phase_split / role_split / custom
  tree_json         TEXT          预置分解树（mode=custom）
  apply_trigger     VARCHAR(32)   on_item_created / on_state_entered / manual
```

**模板的三个硬规则**：

1. **`semantic_state` 不可自定义**。模板里的 `name` 是显示别名——A 模板可以把
   `pending_verification` 叫「待型式试验」，D 模板叫「待回归测试」，但底层语义同一个值，
   所以「四类项目一共有多少工作项卡在待验证」这种统计才成立。**这是跨项目统计一致性的唯一保证，不许破。**
2. **四份模板各自独立版本线**。A 升到 v5 不影响 B 的 v2。
3. **模板升级不推送**。见 §3.3。

## 3. 项目层与模板层的关系规则

### 3.1 创建：模板 → 项目实例

```
project_wf_instance            项目工作流实例
  id                INTEGER PK
  project_id        INTEGER FK project.id  UNIQUE
  template_id       INTEGER FK wf_template.id
  base_version_id   INTEGER FK wf_template_version.id   ← 「基于哪个模板版本」的需求
  current_version_id INTEGER       项目当前生效的版本（迁移后 != base）
  is_customized     BOOLEAN        是否被项目层改过（决定迁移时要不要提示冲突）
  created_at / created_by
  status            VARCHAR(16)    active / migrating / archived
```

创建项目时（现有 `POST /projects` 增加一个可选参数 `template_code`）：

1. 按 `project_type` 找到模板 A 或 B（C/D 是新增项目类型，见 §8）
2. 取该模板 `status='published'` 的最新版本
3. **深拷贝**模板状态/流转/权限到项目级表（`project_wf_state` / `project_wf_transition` / `project_wf_node_acl`）
4. `is_customized = false`，`base_version_id = 当前版本`

**深拷贝而不是引用**，理由：需求四.2 要求项目能改状态数量/名称/顺序。
如果项目直接引用模板行，改一下就会串到所有项目。拷贝是唯一能同时满足
"开箱即用"和"自由调整"的做法。代价是存储冗余，用不上担心（项目数是个位到几十）。

**不传 `template_code` 的老项目**：保持现状，`project_wf_instance` 为空，
现有页面完全不受影响，可以随时"启用工作流"补建实例。

```
project_wf_state               项目状态节点（可自定义）
  id                INTEGER PK
  instance_id       INTEGER FK project_wf_instance.id
  tmpl_state_id     INTEGER       来自哪个模板状态（迁移比对用）
  code / name / semantic_state / phase_code / sort_order / lane
  is_initial / is_terminal / is_verification / wip_limit / color
  is_customized     BOOLEAN       本行是否被项目改过
  UNIQUE(instance_id, code)

project_wf_transition          项目流转规则   —— 结构同 wf_transition_def，加 instance_id
project_wf_node_acl            项目节点权限   —— owner_kind='project', owner_id=project_id
```

### 3.2 调整：项目层改动只影响自己

| 操作 | 允许 | 影响范围 | 约束 |
|---|---|---|---|
| 改状态**名称** | ✅ | 本项目 | — |
| 改状态**顺序** | ✅ | 本项目 | 不得破坏 `is_initial` 唯一性 |
| **增/删**状态 | ✅ | 本项目 | 删除时若有工作项停在该状态，必须先指定迁移目标状态 |
| 改流转规则 | ✅ | 本项目 | 改完做**可达性检查**：每个非终止状态必须有出边 |
| 改节点权限 | ✅ | 本项目 | 必须至少留 1 个 `can_force_drag` 主体，否则 PM 锁死自己 |
| 改 `semantic_state` | ❌ | — | 见 §2 硬规则1 |
| 反向写回模板 | ❌ | — | 需求四.3 明确禁止 |

每次改动写 `audit_log`（`action='update'`, `entity_type='project_wf'`），
`details` 存改动前后的 diff——模板收敛（§3.4）要靠这份数据。

**可达性检查**是必须的：删掉一个状态或改一条流转，很容易造出「进得去出不来」的死状态。
校验规则：从 `is_initial` 出发做 BFS，每个非 `is_terminal` 状态都必须有可达的出边，否则拒绝保存。

### 3.3 迁移：项目 → 新版本模板（手动，先看差异）

需求四.5：PM 可手动选择迁移到新版本，迁移前展示差异。三步入：

```
project_wf_migration           迁移记录
  id / instance_id
  from_version_id / to_version_id
  status            VARCHAR(16)   preview / applied / rolled_back
  diff_json         TEXT          **差异快照**，见下
  state_mapping_json TEXT         旧状态ID → 新状态ID 的映射
  applied_at / applied_by
  rolled_back_at / rolled_back_by
```

**Step 1 — `POST /projects/{id}/workflow/migrate` `{dry_run: true}`，产出差异**：

差异分五类，逐类给"会影响到什么"而不是只列技术 diff：

| 差异类型 | 展示内容 | 影响提示 |
|---|---|---|
| 状态新增 | 名称、语义、顺序 | 「升级后这 N 个状态可用」 |
| 状态删除 | 名称 + **当前停在该状态的工作项数** | 「这 N 条工作项需要你指定迁到哪」 |
| 状态改名 | 旧名 → 新名 | 「仅显示变化，工作项不受影响」 |
| 流转变化 | 新增/删除的边 | 「这些路径将不再可用」 |
| 权限变化 | 谁多了/少了哪个原子 | 「X 人将失去 Y 状态的进入权」 |
| 你的定制冲突 | 项目层改过、模板也改过的行 | 「两边都改过，需逐条决定留哪边」 |

**Step 2 — 人工确认**：删除的状态必须为它下面的工作项指定目标状态（前端给下拉，
按 `semantic_state` 给出推荐默认，如两个状态都是 `done` 则默认互迁）。

**Step 3 — `{dry_run: false}` 应用**，单事务：写新状态行 → 迁工作项 `state_id` →
替换流转/权限 → 更新 `current_version_id` → 写 `project_wf_migration` + `audit_log`。

**回滚**：`project_wf_migration` 保留 `diff_json` 和 `state_mapping_json`，
`POST /projects/{id}/workflow/migrate/rollback` 可还原上一个版本的结构和状态归属。
**回滚窗口 = 到下一次迁移之前**（不像强制拖拽有 24h 限制），因为结构变化是可完整逆的。
但迁移后**新建**的工作项状态在回滚时会丢失归属 → 回滚前必须提示并让 PM 确认。

**`is_customized` 的冲突处理规则**：
`项目改过 && 模板没改` → 保留项目改的；`项目没改 && 模板改了` → 用模板的；
`两边都改` → **不自动决定，列出来让 PM 逐条选**。这条不能省，自动合并会静默吃掉别人的定制。

### 3.4 模板收敛（反哺机制）

需求三.5。做法：定期跑一个**只读**分析任务（`scripts/wf_template_converge.py`），
扫所有 `project_wf_state` / `project_wf_transition` 与基础版本的差异，输出：

- 「≥60% 的项目都加了同一个状态 X」→ 建议进模板
- 「≥60% 的项目都删了状态 Y」→ 建议从模板移除
- 「≥60% 的项目改了同一条流转」→ 建议改模板

**只出报告不自动改模板**。模板变更影响未来所有新项目，必须人拍板。
报告落 `audit_log`（`action='report'`, `entity_type='wf_template'`）。

## 4. 权限矩阵

### 4.1 矩阵本体

**行 = 用户/用户组，列 = 状态节点，单元格 = 四个原子。**

以软件项目 D 模板为例（`●`=允许，`–`=不允许，`△`=需签核）：

| 主体 \ 状态 | 未开始<br>`not_started` | 进行中<br>`in_progress` | 待评审<br>`pending_review` | 待验证<br>`pending_verification` | 已完成<br>`done` | 已阻塞<br>`blocked` |
|---|---|---|---|---|---|---|
| **PM**（隐式，`subject_type='pm'`） | 进● 出● 编● **拽●** | 进● 出● 编● **拽●** | 进● 出● 编● **拽●** | 进● 出● 编● **拽●** | 进● 出● 编● **拽●** | 进● 出● 编● **拽●** |
| 用户：张翔 | — | 进● 出● 编`[progress_pct]` | 进● 出– 编`[review_note]` | — | — | — |
| 组：本项目·软件工程师 | 进● 出● 编● | 进● 出● 编● | 进● 出– 编`[impl_note]` | — | — | 进● 出● 编`[blocker]` |
| 组：本项目·测试工程师 | — | — | 进● 出– 编`[test_case]` | 进● 出● 编● | — | — |
| 组：本项目·项目经理 | （见上 PM 行，二者等价） | | | | | |
| 组：研发部（部门） | — | 进● 出– 编– | 进– 出– 编– | 进– 出– 编– | — | — |
| 组：PP3 评审组（`wf_group`） | — | — | 进● 出● 编`[review_note]` | 进● 出● 编`[verify_result]` | 进● 出– 编– | — |

**读法**：单元格里的 `进/出/编/拽` 就是 `can_enter / can_exit / can_edit_fields / can_force_drag`。
`编` 后面方括号是允许编辑的字段码，空 = 全部。

**四条判定规则**（服务端实现，前端只是把结果画出来）：

1. **PM 行是隐式的**，不需要配，也**不能被配置成关闭**——否则 PM 会把自己锁死。
   判定方式：查 `ProjectMember` 里 `role.name == '项目经理'` 且 `project_id` 匹配。
2. **`can_force_drag` 不继承、取交集、必须显式授予**。模板默认只给 PM。
3. **普通成员跨状态拖拽一律拒绝**（`can_force_drag=false` 时前端不给拖拽手柄，
   后端也返回 403）——这是需求五.4，不能只靠前端。
4. **关键交接节点**（`wf_state_def.is_verification = true` 或 `require_signoff = true`）：
   `can_enter` 必须显式授给具体用户或组；非关键节点允许 `owner_user_id` 自由流转。

### 4.2 矩阵的存储与呈现

矩阵是**稀疏**的：不要给每个(主体×状态)建行，只存非空的授权。上面的表是**渲染结果**，
存储是 `wf_node_acl` / `project_wf_node_acl` 的若干行。

前端建议做成**状态节点为列的可编辑表格**，直接调
`GET /api/projects/{id}/workflow/acl-matrix`（返回渲染好的二维结构，含继承来的行）和
`PUT /api/projects/{id}/workflow/acl-matrix`（只回写被改动的单元格）。

## 5. PM 强制拖拽：审计字段与回退机制

### 5.1 审计日志字段

```
wf_force_drag_log
  id                INTEGER PK
  project_id        INTEGER FK project.id          NOT NULL
  work_item_id      INTEGER FK work_item.id        NOT NULL

  -- 变更内容
  from_state_id     INTEGER FK project_wf_state.id
  from_state_code   VARCHAR(32)    快照，状态被删后日志仍可读
  from_state_name   VARCHAR(64)    快照
  from_semantic     VARCHAR(16)    快照（标准语义，统计用）
  to_state_id       INTEGER FK project_wf_state.id
  to_state_code / to_state_name / to_semantic      同上快照

  -- 操作人
  operator_user_id  INTEGER FK user_auth.id
  operator_username VARCHAR(64)    冗余，风格同 audit_log.username
  operator_is_pm    BOOLEAN        操作时是否确为该项目 PM（防止事后角色变更导致日志失真）

  -- 跳过原因（跳过验证节点时必填）
  reason            TEXT           **跳过原因**
  reason_required   BOOLEAN        本次是否强制要求填原因
  skipped_states    TEXT           JSON: [{id, code, name, semantic, is_verification}]
                                   ← 被跳过的验证节点清单

  -- 副作用追踪
  effect_count      INTEGER        本次产生的副作用条数
  has_unrevertable  BOOLEAN        是否存在不可撤销的副作用

  -- 回退
  is_reverted       BOOLEAN  default 0
  reverted_by       VARCHAR(64)
  reverted_at       DATETIME
  revert_reason     TEXT
  superseded_by_id  INTEGER FK wf_force_drag_log.id   ← 被后续操作覆盖

  created_at        DATETIME       NOT NULL
  INDEX(project_id, created_at)
  INDEX(work_item_id, created_at)
  INDEX(operator_username, created_at)
```

**同时写现有 `audit_log`**：`action='force_drag'`、`entity_type='work_item'`、
`entity_id=work_item_id`、`project_id`、`summary` 形如
`「PM 强制变更：进行中 → 已完成（跳过 待验证），原因：客户口头放行」`。
这样现有的审计页面立刻能查到，不用新开入口。

### 5.2 副作用的记录（回退的前提）

强制拖拽**不是只改一个字段**，它按需求会连带做四件事。每件都要能撤销：

```
wf_force_drag_effect           强制拖拽的副作用台账
  id                INTEGER PK
  force_drag_id     INTEGER FK wf_force_drag_log.id
  seq               INTEGER
  effect_type       VARCHAR(32)   notify / create_task / run_automation / set_field / webhook
  payload_json      TEXT          足够重建/撤销的数据
  compensable       BOOLEAN
  compensation_json TEXT          怎么撤（撤销后填实际做了什么）
  status            VARCHAR(16)   applied / compensated / compensation_failed
  created_at / compensated_at
```

| 副作用 | 是否可补偿 | 怎么补 |
|---|---|---|
| 状态同步通知（负责人+相关角色） | ✅ | 发反向通知「上述变更已撤销」 |
| 「补验证」待办任务 | ✅ | 置为 `cancelled`，不物理删除（留痕） |
| 触发的 post_transition 自动化 | ⚠️ 逐条看 | 动作级补偿，见 §6.3 |
| 外部 webhook | ❌ | **不可撤**，`has_unrevertable=1` |
| 字段被自动化改写 | ✅ | 用 `payload_json` 里的旧值写回 |

### 5.3 回退机制

**入口**：`POST /api/projects/{id}/workflow/force-drag/{log_id}/revert`，
权限 = PM 或 `can_force_drag`。

**执行顺序（必须逆序补偿，且单事务）**：

1. 前置校验
   - `is_reverted=0`
   - `created_at` 在**回退窗口内**（默认 24h，可配 `project.wf_revert_window_hours`）
   - 该工作项**没有在这个状态之后被别的操作动过**（`superseded_by_id IS NULL`）
2. 写入 `reverted_by/at/reason`（先落痕，避免补偿中途失败后无记录）
3. **逆序**执行 `wf_force_drag_effect` 的补偿：取消补验证任务 → 撤回通知 → 回写字段 → 补偿自动化
4. 把 `work_item.state_id` 写回 `from_state_id`，`state_entered_at` 恢复
5. 对不可补偿的项，**收集成清单返回**：「以下 2 项无法自动撤销：已发出的外部 webhook、…」
6. 写 `audit_log`（`action='revert'`）

**四条硬规则**：

1. **超过窗口不能回退**，只能再走一次强制拖拽正向修——留痕比"假装没发生"重要。
2. **有不可补偿副作用时，回退前必须二次确认**，把清单摆给 PM 看。
3. **补偿失败不回滚已完成的补偿**：记录 `status='compensation_failed'` 并告警，
   一条一条来，不允许"补偿也失败了就整批回滚"。
4. **回退本身也走审计**，且 `wf_force_drag_log` 一行不删。

### 5.4 强制拖拽的完整事务边界

```
BEGIN
  ├─ 校验 can_force_drag
  ├─ 计算 skipped_states（见下）
  ├─ 若跳过验证节点 → 校验 reason 非空，否则 400
  ├─ UPDATE work_item.state_id（乐观锁 version）
  ├─ INSERT wf_force_drag_log
  ├─ INSERT wf_force_drag_effect ×N（先写"打算做什么"，status=pending）
  ├─ INSERT audit_log
  └─ INSERT notification_outbox ×N     ← 通知走 outbox，不发同步调用
COMMIT
   ↓ 提交后异步
  发通知 / 建补验证任务 / 跑 post_transition 自动化
  （各自回写 effect.status，失败的进入重试）
```

**通知必须走 outbox**：外部通知（钉钉/邮件）会超时和失败，绝不能让它把状态变更事务拖垮。
这是从现有 `webhook_config.failure_count` 的教训来的。

**"跳过验证节点"的判定**（要可解释，PM 得看懂为什么弹框）：

```
skipped = [ s for s in 本泳道内排序在 from 和 to 之间的状态
            if s.is_verification and s 不在 from→to 的最短路径上 ]
```

即：**同泳道内按 `sort_order` 落在区间里、且图上的最短路径不经过它**的验证节点。
跨泳道（`lane` 不同）不算跳过——比如从"研发部·进行中"拖到"测试部·待验证"，
中间隔着别的泳道，那是正常交接不是跳过。

另加显式兜底：`wf_transition_def.must_pass_states` 里声明必须经过的状态，
被绕过时同样触发确认框+补验证。

## 6. 自动化规则清单

### 6.1 触发事件（触发器原子）

| event | 触发时机 | 可用字段（condition 里能引用） |
|---|---|---|
| `item.created` | 工作项创建 | `item.type` `item.priority` `item.owner` `item.attrs.*` |
| `state.entered` | 进入状态 | `+ state.code` `state.semantic` `state.entered_at` |
| `state.exited` | 离开状态 | `+ from_state.*` `state.dwell_hours`（停留时长） |
| `transition.requested` | 流转**请求**（pre 相位） | `from_state` `to_state` `operator` `is_force_drag` |
| `field.changed` | 字段变更 | `+ field.code` `field.old` `field.new` |
| `relation.added` | 关系建立 | `+ relation.kind` `relation.code` `relation.other` |
| `signoff.completed` | 签核完成 | `+ signoff.level` `signoff.result` `signoff.signer` |
| `gate.reviewed` | 阶段门评审 | `+ gate.code` `gate.result`（复用现有 `gate_signoff_record`） |
| `dependency.cleared` | 阻塞解除 | `+ blocking_item` |
| `schedule.cron` | 定时 | cron 表达式 |
| `manual` | 人工触发 | — |

### 6.2 条件表达式（`condition_json`）

保持**可读、可校验、不引入脚本引擎**（不 eval）：

```json
{"all": [
  {"field": "item.priority", "op": "in", "value": ["P0", "P1"]},
  {"field": "state.dwell_hours", "op": "gt", "value": 72},
  {"any": [
    {"field": "item.attrs.severity", "op": "eq", "value": "高"},
    {"field": "relation.exists", "op": "eq",
     "value": {"kind": "dependency", "code": "blocks", "direction": "in"}}
  ]}
]}
```

支持的 `op`：`eq ne gt gte lt lte in not_in contains is_null is_not_null exists`。
字段引用一律走白名单解析，未知字段**校验期就报错**，不留到运行时。

### 6.3 动作类型（动作原子 + 可补偿性）

| action_type | 参数 | 可补偿 | 补偿动作 |
|---|---|---|---|
| `set_field` | `{field, value}` | ✅ | 写回旧值 |
| `assign_user` | `{user_id 或 "role:测试工程师"}` | ✅ | 还原旧 owner |
| `create_work_item` | `{item_type, title, state_code, parent_to: "self"}` | ✅ | 置 `cancelled` + 断关系 |
| `create_relation` | `{kind, code, to: "..."}` | ✅ | 删除该关系 |
| `create_todo` | `{title, assignee, due_days, phase}` | ✅ | 置 `cancelled` |
| `notify` | `{to:["owner","pm","group:测试组"], template}` | ✅ | 发反向通知 |
| `require_signoff` | `{level, signer}` | ✅ | 撤回签核请求 |
| `set_due_date` | `{field, offset_days}` | ✅ | 写回旧值 |
| `webhook` | `{config_id 或 url, payload}` | ❌ | **不可撤**，只能记录 |
| `ai.structure` | `{source_field, target_attrs}` | ✅ | 清空目标属性 |
| `ai.analyze` | `{kind:"risk"\|"similar_defect", output_to}` | ✅ | 清空输出 |
| `ai.suggest` | `{target:"state"\|"owner", output_to}` | ✅ | 清空建议 |
| `block_transition` | `{message}` | — | 只用于 `pre_transition` 相位 |

### 6.4 失败回退策略（`on_failure`）

**核心设计决定：把规则按相位分成两类，回退语义完全不同。**

```
pre_transition 规则（流转前跑）
  ├─ 失败 → block_transition：**流转根本不发生**
  │        用户看到明确原因，状态没变过，不需要任何回退
  │        ← 这是最干净的"回退"：让它别发生
  └─ 适用：必填字段校验、依赖未清、交付物未齐、权限预检

post_transition 规则（流转后跑）
  ├─ retry：按 retry_backoff 重试 retry_max 次
  ├─ compensate：逆序执行动作级补偿
  └─ **不回滚状态流转**
       理由：状态已经对用户可见，别人可能已经开始基于新状态干活了；
       静默回滚比"部分失败+明确告警"更糟。
       （同一条理由见上一轮权限改造：改部门矩阵静默改掉二十个人权限，当时也是选的不做）
```

**失败处理四步**：① 记 `wf_automation_run.status='failed'` + `error` →
② 按 `on_failure` 执行 → ③ 写 `audit_log`（`action='wf_auto'`）→ ④ 若 `on_failure=compensate`
且补偿也失败，**升级告警**给 PM（通知 + 项目健康度打标）。

### 6.6 AI 连接点

需求六.4：AI 只做结构化、分析、重试；最终验收由人决定。
项目推进 = **项目事实 + AI 执行流程 + 专业工具证据 + 人工决定**。

四条硬约束（写进代码，不靠自觉）：

1. **AI 动作永远不能写 `work_item.state_id`**。`ai.suggest` 只能写到一个
   `wf_ai_evidence` 记录里，由人确认后走**正常的 transition**。这条是防止 AI 越权改状态。
2. **每个 AI 输出必须带证据**，落 `wf_ai_evidence`：

```
wf_ai_evidence
  id / project_id / work_item_id
  kind              VARCHAR(32)   structure / analyze / suggest / retry
  input_digest      TEXT          输入摘要（不存全文，避免库膨胀）
  model             VARCHAR(64)   模型 ID
  prompt_version    VARCHAR(32)   prompt 模板版本 ← 可追溯同一问题不同 prompt 的表现
  output_json       TEXT
  confidence        REAL
  accepted_by       VARCHAR(64)   人工采纳人
  accepted_at       DATETIME
  rejected_reason   TEXT
  created_at
```

3. **人工决定留痕**，落 `wf_decision_record`：

```
wf_decision_record
  id / project_id / work_item_id
  decision          VARCHAR(32)   accept_ai / reject_ai / override / verify_pass / verify_fail
  based_on_evidence_id  INTEGER FK wf_ai_evidence.id   ← 这次决定基于哪条证据
  decided_by        VARCHAR(64)
  decided_at        DATETIME
  note              TEXT
```

4. **"专业工具证据"也是一等公民**。型式试验报告、仿真结果、测试结果这些由外部工具产生的
   证据，通过现有 `deliverable` / `deliverable_attachment` / `test_result` 挂到工作项上
   （用 `work_item_source_map` 或 `verifies` 关系），AI 的分析必须引用具体证据 ID，
   不允许无来源的结论。

**重试的边界**：AI 调用的失败重试由自动化引擎的 `retry` 机制负责，
但 **`retry_max` 默认 3、且重试必须复用同一个 `idempotency_key`**——
否则一次网络抖动会产生多条重复的 AI 建议。

## 7. 关系模型：哪些对象之间要建哪种关系

### 7.1 关系地图

| 从 | 到 | 关系原子 | 具名 code | 说明 |
|---|---|---|---|---|
| 需求 | 需求 | 层级 | `parent_child` | 需求分解 |
| 需求 | 任务 | 层级 | `parent_child` | 需求拆任务（现有 `Task.parent_id` 的语义升级） |
| 任务 | 任务 | 层级 | `parent_child` | WBS 分解（**现有 `task.parent_id` 直接映射**） |
| 需求 | 任务 | 依赖 | `depends_on` | 任务依赖需求冻结 |
| 任务 | 任务 | 依赖 | `blocks` | 前后置（**现有 `milestone.depends_on_id` 的通用化**） |
| 缺陷 | 需求 | 具名关联 | `verifies` | 缺陷验证需求符合性 |
| 缺陷 | 缺陷 | 具名关联 | `duplicates` | 重复缺陷（对称） |
| 缺陷 | 缺陷 | 具名关联 | `causes` | 根因链 |
| 缺陷 | 变更 | 具名关联 | `introduces` | 哪个变更引入了它 |
| 测试项 | 需求 | 具名关联 | `verifies` | 测试覆盖需求（**追溯矩阵的来源**） |
| 变更请求 | 需求 | 具名关联 | `introduces` | 变更引入了新需求 |
| 变更请求 | 交付物 | 具名关联 | `introduces` | 变更影响交付物 |
| 风险 | 任务 | 具名关联 | `relates_to` | 风险的缓解任务（对称） |
| 风险 | 风险 | 层级 | `parent_child` | 风险分解（大风险拆子风险） |
| 交付物 | 工作项 | 具名关联 | `verifies` | 交付物是某项的验收证据 |
| 工作项 | 阶段 | — | 不用关系表 | 走 `wf_state.phase_code`，不建关系 |

### 7.2 与现有表的关系

**不改造现有关系字段，只做映射**：

| 现有 | 现状 | 新引擎怎么接 |
|---|---|---|
| `task.parent_id` | 自引用，WBS | 首次被新引擎触碰时，转成 `hierarchy/parent_child` 关系行；老字段保留不动 |
| `milestone.depends_on_id` | 单值前置 | 同上，转成 `dependency/depends_on`；注意它是**单值**，新模型是多值 |
| `requirement.deliverable_id` | 需求→交付物 | 转成 `link/relates_to` |
| `bom_item.parent_id` | BOM 层级 | **不接**——BOM 是物料清单不是工作项，别硬塞进关系模型 |

### 7.3 关系的自动校验（服务层）

| 校验 | 触发时机 | 失败处理 |
|---|---|---|
| 成环检测 | 建/改任何关系 | 拒绝，返回环路径给前端：「A → B → C → A」 |
| 单父约束 | 建 `hierarchy` | 拒绝，提示已有父项 |
| 阻塞传播 | 建 `FS` 依赖 / 清依赖 | 更新 `to_item.is_blocked`，写审计 |
| 跨项目限制 | 建关系 | 默认拒绝；`wf_relation_kind.allow_cross_project=1` 才放行 |
| 状态一致性 | 父项已 `done` 而子项新建 | 警告（不拒绝）：「父项已完成，确认要加子项？」 |

**成环检测用递归 CTE**，在一条 SQL 里跑完，不要拉全表到内存里做 DFS：

```sql
WITH RECURSIVE reach(id) AS (
  SELECT :to_item_id
  UNION
  SELECT r.to_item_id FROM work_item_relation r
    JOIN reach ON r.from_item_id = reach.id
   WHERE r.kind IN ('hierarchy','dependency')
)
SELECT 1 FROM reach WHERE id = :from_item_id LIMIT 1;   -- 有行 = 会成环
```

## 8. 四类模板的差异化设计框架

### 8.1 与现有 `project_type` 的映射（**这是最容易踩坑的地方**）

现有 `project.project_type` 只有 `hardware` / `software` 两个值（13 + 4 个项目）。
四类模板必须先解决"怎么落到这个只有两值的字段上"。

**方案：新增一个 `project.wf_template_code` 列，不动 `project_type`。**
理由：`project_type` 被 51 处代码引用（阶段种子、页签配置、交付物标准、工作流白名单…），
改它的语义会连带炸掉一大片；新加一列只被新引擎读，零风险。

| 模板 | 类别 | 现有 `project_type` | 新增 `wf_template_code` | 现在的项目 |
|---|---|---|---|---|
| A 电机电控系统集成开发 | 合同交付类 | `hardware` | `A` | 13 个，含金浪 |
| B 电机软件研发定制 | 合同交付类 | `software` | `B` | 4 个 |
| C 电机产品开发 | 内部研发类 | `hardware` | `C` | 暂无 |
| D 软件开发 | 内部研发类 | `software` | `D` | 暂无 |

**关键**：C 复用 `hardware` 的阶段/交付物标准体系，D 复用 `software` 的，
但**工作流模板是独立的**。现有 17 个项目 `wf_template_code` 留空（NULL），
行为完全不变；新项目创建时按 (类别, 类型) 自动推荐对应模板。

### 8.2 四类模板的关键差异点

需求说不需要具体状态列表，所以这里只给**差异维度**和每类的取值倾向。

| 维度 | A 合同交付类·电控集成 | B 合同交付类·软件定制 | C 内部研发类·产品开发 | D 内部研发类·软件开发 |
|---|---|---|---|---|
| **需求来源** | 客户技术协议/SOR，逐条冻结 | 客户功能清单 + UAT 条款 | 市场需求 + 竞品分析 + 内部立项 | 产品路线图 + 内部用户反馈 |
| **需求冻结时机** | P0 结束前必须冻结（合同约束） | S0 结束前冻结 SRS | 立项评审通过后冻结 | 迭代规划会冻结 |
| **交付物形态** | 实物样机 + 全套图纸 + 试验报告 | 可运行软件包 + 部署文档 + 源码 | 样机 + 设计文档 + 工艺文件 | 软件版本 + 文档 |
| **验证方式** | 型式试验/可靠性/环境/EMC/**客户送样** | 集成/性能/UAT/**客户试用** | 内部台架验证 + 设计评审 | 自动化测试 + 内部试用 |

| **甲方/验收主体** | **外部客户**（验收有法律意义） | **外部客户** | 内部（产品委员会） | 内部（产品负责人） |
| **变更控制** | **强**：ECN + 两级签核（现有 `change_signoff_record`） | 中强：变更两级签核 | 中：内部变更评审 | 弱：走版本迭代，不单独走变更流程 |
| **成本口径** | 合同额 / 回款 / 实际成本（**现有财务模型**） | 合同额 / 回款 | **预算 / 投入人力工时**（通常无回款） | 预算 / 人力工时 |
| **关键风险** | 长周期物料、供应商、客户变更 | 需求蔓延、客户环境差异 | 技术路线失败、市场窗口 | 需求不稳定、技术债 |
| **状态机宽度** | 宽（20+ 状态，跨阶段多泳道） | 宽（18+ 状态） | 中（12-15 状态） | **窄（8-10 状态）** |

### 8.3 四类模板的共用底座

**不允许差异化**的部分（否则跨项目统计失效）：

1. `semantic_state` 七值枚举——所有模板的所有状态必须映射到它
2. 关系三原子——四类模板用同一套 `wf_relation_kind`
3. 权限四原子——`can_enter/can_exit/can_edit_fields/can_force_drag`
4. 自动化四原子——触发/动作/失败回退/审计的结构
5. PM 超级权限——四类模板的 PM 都能强制拖拽（严格度可调，权限本身不能没有）

**允许差异化**的部分：状态数量与名称、流转拓扑、验证节点密度、默认权限、
默认任务分解、自动化规则默认集、验证节点跳过时的补偿强度。

### 8.4 模板 A/B 的 v1 基线来源

模板 A、B 的 v1 **不重新设计**，直接从现有 `PHASE_NODES` 导入：

```
PHASE_NODES[阶段码] → wf_state_def 的映射规则：
  节点 seq 顺序      → sort_order
  节点 name          → name
  节点 venue='线下'   → 该状态额外标记 needs_offline_confirm=true
                       （接现有 project_workflow_step_confirm）
  节点 roles[]       → 默认 wf_node_acl_def 行（subject_type='project_role'）
  节点 output        → 挂到现有 gate_deliverable_standard（通过 workflow_map 已有映射）
  阶段末位节点        → is_verification=true + require_signoff=true（它就是门禁）
  阶段码             → phase_code 字段（汇总回现有阶段视图）
```

这样 v1 基线导入后，**模板 A 在平台上的行为与今天的 `PHASE_NODES` 完全一致**，
新引擎的引入对现有 13 个硬件项目是**零感知**的（它们不建实例，页面照旧）。

## 9. 按团队规模的简化建议

核心判断：**状态机的复杂度应该跟团队规模成反比**。人少的时候，流程的成本全落在
"维护流程"上，收益是负的。

| | 小团队（≤10 人） | 中等（11-30 人） | 大（>30 人） |
|---|---|---|---|
| **用哪个模板** | 直接用模板默认，**不做项目层自定义** | 模板默认 + 少量状态调整 | 全功能 |
| **状态数量** | ≤8 个（未开始/进行中/待评审/待验证/已完成/已阻塞/已取消） | 10-15 个 | 15-25 个 |
| **验证节点** | 只留阶段末 1 个 | 关键交接 2-4 个 | 全部关键节点 |
| **权限配置** | **只配 PM + 部门级**，不配到人 | 关键节点配到人/组，其余按部门 | 全节点配到人/组 |
| **强制拖拽** | 保留（PM 兜底用），但**不要求填原因**（`reason_required=false`） | 跳过验证节点时要求填原因 | 全部要求填原因 + 二次确认 |
| **自动化规则** | 只开 4 条：阻塞通知、逾期提醒、评审提醒、补验证 | 开 §6.5 里的 1-9 条 | 全开 + 自定义 |
| **关系模型** | 只用层级 + 阻塞（`blocks`） | 三种都用 | 三种都用 + 跨项目依赖 |
| **AI 连接点** | 不用 | 只开 `ai.structure`（省录入成本） | 全开 |
| **模板收敛参与** | 只读报告 | 只读报告 | 有反馈通道 |
| **落地顺序** | 先跑通"状态流转 + 看板"，两周后再谈自动化 | 同上 + 权限矩阵 | 分三期 |

**一句话规则**：**新团队/新项目一律先用最简配置跑满一个月**，
等有人开始抱怨"这个流程卡住我了"，再按抱怨的具体点加配置——
**不要让 PM 在第一天就面对一张 20×N 的权限矩阵**，那是这个功能最容易死的地方。

**给 10 人以下团队的具体默认值**（建议直接做成"简单模式"开关）：

```
状态: 7 个固定（七种语义状态一对一，名称可改）
流转: 允许任意状态互转（不配 guard），但 done 不可逆（除 PM 强制）
权限: PM 全权；其余人 can_enter/can_exit 全开，can_edit_fields 全开，can_force_drag 全关
      → 等价于"能推状态但推错了要 PM 修"
验证节点: 只有阶段末节点 is_verification=true
自动化: 阻塞通知 + 逾期提醒
```

## 10. 落地切分与风险

### 10.1 建议分三期

| 期 | 内容 | 交付判据 |
|---|---|---|
| **一期（地基）** | `work_item` 元模型 + `work_item_relation` 三关系 + `wf_template`/`wf_state_def`/`wf_transition_def` + `project_wf_*` + 模板 A/B 从 `PHASE_NODES` 导入 v1 + 基础看板与流转接口 | 老项目零感知；新建一个软件项目能跑通"需求：未开始→进行中→待评审→已完成" |
| **二期（权限与强制）** | `wf_node_acl` + 权限矩阵 UI + 强制拖拽 + `wf_force_drag_log`/`effect` + 回退 + 通知 outbox | PM 强制拖拽能留痕、能回退；普通成员绕接口也推不动 |
| **三期（自动化与 AI）** | `wf_automation_rule`/`run`/`action_log` + 规则清单 1-16 + `wf_ai_evidence` + `wf_decision_record` + 模板 C/D | 规则 1/4/8/10 在真实项目跑一周无异常；AI 建议全部留痕且不能改状态 |

### 10.3 效力边界（必须写进交付说明）

现有平台的**接口层校验只有 19 处** `require_permission`，14 个模块**只靠前端隐藏菜单**。
本次引擎的权限原子如果也只在接口做一半，等于没做——状态权限是**要拦住绕过界面的调用**才有意义。

所以：**状态权限（`can_enter/can_exit/can_edit_fields/can_force_drag`）必须在服务端
流转接口强制校验**，这与上一轮"模块权限暂不补接口校验"的决定**不冲突**——
上一轮不补的是"你能不能打开这个页面"，这一轮必须补的是
"你能不能动这一条工作项"，后者的越权后果是**流程被静默破坏**，代价高得多。

建议的校验落点（新接口，都不碰现有接口的行为）：
- `POST /api/work-items/{id}/transition` —— 校验 `can_exit(from) + can_enter(to) + guard_json`
- `POST /api/work-items/{id}/force-transition` —— 校验 `can_force_drag` + reason
- `PUT /api/work-items/{id}/fields` —— 校验 `can_edit_fields`
- `POST /api/work-items/{id}/relations` —— 校验成环 + 跨项目限制
